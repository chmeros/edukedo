# Thema 9.3 — Versionsverwaltung

## Theorie

### Wozu Versionsverwaltung?

In den Softwareprojekten der **Brevanta IT-Systemhaus GmbH** arbeiten mehrere Entwickler:innen gleichzeitig an derselben Anwendung, etwa am Kundenportal. Ohne Werkzeug entstehen schnell Dateien wie `portal_final_neu2.zip` und Überschreibkonflikte. Eine **Versionsverwaltung** (Version Control System, VCS) löst das: Sie speichert jede Änderung mit Autor:in, Zeitpunkt und Begründung, erlaubt die Rückkehr zu früheren Ständen, ermöglicht paralleles Arbeiten an verschiedenen Aufgaben (Zweige) und markiert Releases. Der Ausbildungsrahmenplan der Fachrichtung Anwendungsentwicklung nennt den Einsatz von Werkzeugen zur Versionsverwaltung ausdrücklich als Teil der Berufsbildposition „Sicherstellen der Qualität von Softwareanwendungen" (§ 4 Absatz 3 Nummer 2 FIAusbV). Versioniert werden nicht nur Quelltext, sondern auch Konfigurationen, Skripte, Dokumentation und Datenbankmigrationen. Eine Versionsverwaltung ist **kein Ersatz für ein Backup**, und große Binärdateien sowie Geheimnisse (siehe Thema 9.1) gehören nicht hinein.

### Zentrale und verteilte Versionsverwaltung

Bei **zentralen Systemen** (z. B. CVS, Subversion) liegt das Repository auf einem Server; Entwickelnde holen nur eine Arbeitskopie und übertragen Änderungen direkt dorthin. Ohne Serververbindung ist das Arbeiten stark eingeschränkt, und der Server ist ein Single Point of Failure.

Bei **verteilten Systemen** (z. B. Git, Mercurial) besitzt jeder Klon ein **vollständiges Repository mit der gesamten Historie**. Änderungen werden zuerst lokal festgehalten (Commit) und später mit anderen Repositories abgeglichen (Push, Pull). Das ermöglicht Offline-Arbeit, schnelle Operationen und sehr leichtgewichtige Zweige. Heute dominiert **Git**. Zu unterscheiden sind die Software Git und Plattformen, die Remote-Repositories hosten und zusätzliche Funktionen wie Merge-Requests, Ticketverwaltung und CI-Pipelines anbieten (z. B. GitHub, GitLab oder ein selbst betriebener Server).

### Git-Grundbegriffe

- **Repository:** Datenbank der Versionshistorie eines Projekts (lokal und/oder auf einem Remote-Server).
- **Arbeitsverzeichnis (Working Directory):** die aktuell ausgecheckten, bearbeitbaren Dateien.
- **Staging Area (Index):** Zwischenablage, in der festgelegt wird, welche Änderungen in den nächsten Commit eingehen.
- **Commit:** unveränderlicher Schnappschuss des Projektstands mit eindeutigem Hash, Autor:in, Zeitstempel, Nachricht und Verweis auf den Vorgänger-Commit.
- **Branch (Zweig):** beweglicher Zeiger auf einen Commit; ein neuer Commit verschiebt den Zeiger des aktuellen Zweigs. Der Hauptzweig heißt heute üblicherweise `main`.
- **HEAD:** Verweis auf den aktuell ausgecheckten Stand (meist auf den aktuellen Zweig).
- **Merge:** Zusammenführen der Änderungen eines Zweigs in einen anderen.
- **Konflikt:** Git kann zwei Änderungen nicht automatisch vereinen, weil beide dieselbe Stelle betreffen.
- **Tag:** feste, benannte Markierung eines Commits, typischerweise für Releases (z. B. `v1.2.0`).
- **Remote:** Repository auf einem anderen Rechner/Server; das Standard-Remote heißt meist `origin`.
- **Pull Request / Merge Request:** Antrag auf Übernahme eines Zweigs in einen anderen, verbunden mit Review und automatischen Prüfungen (Begriff je nach Plattform).

### Die vier Bereiche und der Weg einer Änderung

Eine Änderung durchläuft in Git vier Bereiche:

1. **Arbeitsverzeichnis:** die Dateien, wie sie im Projektordner liegen und bearbeitet werden. Hier entstehen Änderungen (geändert, neu, gelöscht), die Git noch nicht festgehalten hat.
2. **Staging-Bereich (Index):** Hier wird mit `git add` vorgemerkt, welche Änderungen in den nächsten Commit eingehen. So lässt sich ein Commit gezielt zusammenstellen, auch aus nur einem Teil der geänderten Dateien.
3. **Lokales Repository:** die Historie auf dem eigenen Rechner (Ordner `.git`). `git commit` schreibt die vorgemerkten Änderungen als Commit hinein. Commits sind hier gesichert, aber für andere noch unsichtbar.
4. **Remote-Repository:** das Repository auf einem Server (z. B. `origin`), über das das Team zusammenarbeitet. `git push` überträgt lokale Commits dorthin.

```
Arbeitsverzeichnis --git add--> Staging-Bereich --git commit--> Lokales Repository --git push--> Remote-Repository
Remote-Repository  --git fetch--> Lokales Repository --git merge--> Arbeitsverzeichnis
```

`git fetch` holt neue Commits des Remotes in das lokale Repository, ohne das Arbeitsverzeichnis zu ändern. `git pull` ist die Kurzform für `git fetch` und anschließendes `git merge` und berührt deshalb mehrere Bereiche. Zurück geht es mit `git restore --staged <datei>` (aus dem Staging-Bereich zurück ins Arbeitsverzeichnis, die Änderung bleibt in der Datei) und `git restore <datei>` (verwirft Änderungen im Arbeitsverzeichnis, nicht rückholbar). Der Befehl `git status` zeigt, welche Änderungen in welchem Bereich liegen. Merksatz: **add** bereitet vor, **commit** sichert lokal, **push** teilt mit dem Team, **fetch** holt nur, **pull** holt und führt zusammen.

### Wichtige Kommandos im Überblick

Ein typischer Ablauf für eine Änderung:

```
git clone https://git.example.org/brevanta/kundenportal.git
git switch -c feature/rechnungs-export
git status
git add rechnung.py
git commit -m "Rechnungsexport als CSV ergänzen"
git push -u origin feature/rechnungs-export
```

Erläuterung: `git clone` kopiert ein Remote-Repository samt Historie. `git switch -c` legt einen neuen Zweig an und wechselt dorthin. `git status` zeigt geänderte, gestagte und unversionierte Dateien. `git add` übernimmt Änderungen in die Staging Area, `git commit` schreibt sie als neuen Commit ins lokale Repository, und `git push -u origin <zweig>` überträgt den Zweig zum Remote und merkt sich die Zuordnung.

Weitere häufig benötigte Kommandos:

```
git log --oneline --graph
git diff
git fetch
git pull
git switch main
git merge feature/rechnungs-export
git tag -a v1.2.0 -m "Release 1.2.0"
git push origin v1.2.0
git restore --staged rechnung.py
git revert <commit-hash>
git stash
```

`git log --oneline --graph` zeigt die Historie kompakt, `git diff` die noch nicht gestagten Änderungen. `git fetch` lädt neue Commits vom Remote, ohne den eigenen Arbeitsstand zu verändern; `git pull` führt standardmäßig `fetch` und anschließend `merge` aus. `git switch main` wechselt in den Hauptzweig, `git merge <zweig>` führt dort einen Zweig ein. `git tag -a` legt einen annotierten Tag an; Tags werden nicht automatisch gepusht, sondern mit `git push origin <tag>` übertragen. `git restore --staged <datei>` nimmt eine Datei wieder aus der Staging Area. `git revert <hash>` erzeugt einen **neuen** Commit, der die Änderungen eines früheren Commits rückgängig macht und dadurch die Historie erhält — im Unterschied zu zerstörerischen Befehlen wie `git reset --hard`, die Änderungen verwerfen. `git stash` legt nicht committete Änderungen vorübergehend beiseite.

### Merge, Fast-Forward und Konflikte

Hat sich der Zielzweig seit dem Abzweigen nicht verändert, genügt beim Merge ein **Fast-Forward**: Der Zeiger wird einfach vorgerückt, es entsteht kein zusätzlicher Commit. Haben sich beide Zweige weiterentwickelt, erzeugt Git einen **Merge-Commit** mit zwei Vorgängern. Ändern beide Seiten **dieselben Zeilen** einer Datei (oder ändert eine Seite eine Datei, die die andere löscht), entsteht ein **Konflikt**. Git markiert die Stelle in der Datei:

```
<<<<<<< HEAD
rabatt = 0.05
=======
rabatt = 0.07
>>>>>>> feature/rabatt-staffel
```

Der Bereich zwischen `<<<<<<<` und `=======` zeigt den Stand des aktuellen Zweigs, der Bereich bis `>>>>>>>` den Stand des einzuführenden Zweigs. Zur Auflösung wird die Datei bearbeitet (die gewünschte endgültige Fassung herstellen, alle Markierungen entfernen), dann mit `git add <datei>` als gelöst markiert und der Merge mit `git commit` abgeschlossen; `git merge --abort` bricht ihn ab. Ist die Fachlogik betroffen (hier: welcher Rabattsatz gilt?), wird die Lösung mit den Beteiligten abgestimmt. Nach der Auflösung laufen die Tests erneut.

Alternativ zum Merge gibt es **Rebase**: Die eigenen Commits werden auf eine neue Basis „umgesetzt", wodurch eine lineare Historie entsteht. Dabei werden Commits neu geschrieben. Deshalb gilt die Regel: **Bereits geteilte (gepushte) Commits werden nicht rebased oder per Force-Push überschrieben**, weil sonst die Historie der Kolleg:innen bricht.

### Branching-Strategien im Grundprinzip

- **Feature-Branch-Workflow:** Jede Aufgabe (Funktion, Fehlerbehebung) bekommt einen eigenen kurzlebigen Zweig, der nach Review in `main` zusammengeführt wird.
- **GitHub Flow:** Spezialisierung davon: `main` ist stets auslieferbar, Änderungen laufen über kurzlebige Zweige und Pull Requests; nach dem Merge kann direkt ausgeliefert werden.
- **Git Flow:** Zusätzlich zu `main` gibt es einen Entwicklungszweig `develop` sowie `feature/*`-, `release/*`- und `hotfix/*`-Zweige. Geeignet für Produkte mit geplanten Release-Zyklen, aber mit mehr Organisationsaufwand.
- **Trunk-Based Development:** Sehr kurzlebige Zweige oder direkte Commits auf den gemeinsamen Hauptzweig, gestützt auf starke Testautomatisierung und Feature-Schalter für unfertige Funktionen.

Welche Strategie passt, hängt von Teamgröße, Releasezyklus und Automatisierungsgrad ab. In allen Varianten wird der Hauptzweig typischerweise **geschützt** (kein direktes Pushen, Merge nur nach erfolgreichem Build und Review).

### Pull-/Merge-Request und Review

Ein Merge-Request läuft meist so ab: Zweig pushen, Request anlegen und beschreiben, automatische Prüfungen (Build, Tests, Scans) laufen lassen, Review durch mindestens eine weitere Person, Rückmeldungen einarbeiten, Zweig in den Hauptzweig übernehmen (als Merge-Commit, als zusammengefasster „Squash"-Commit oder per Rebase). Im Review achten die Prüfenden auf Lesbarkeit, Logik, fehlende Tests, Sicherheitsaspekte (siehe Thema 9.1) und die Einhaltung der Teamregeln. Kleine, fokussierte Requests lassen sich besser prüfen als riesige.

### Sinnvolle Commit-Nachrichten und Zusammenarbeit im Team

Eine gute Commit-Nachricht erklärt, **was** sich geändert hat und vor allem **warum**. Bewährte Regeln: kurze, aussagekräftige Betreffzeile (Richtwert höchstens etwa 50 Zeichen), dann eine Leerzeile und bei Bedarf ein Text mit Begründung und Ticketverweis. Ein Commit soll eine **logisch zusammenhängende** Änderung enthalten („atomar") und das Projekt lauffähig lassen.

```
Rabattstaffel für Großbestellungen ergänzen

Ab 50 Stück gilt 10 % Rabatt, ab 10 Stück 5 %. Die Grenzwerte sind
durch Modultests abgesichert. Refs: Ticket KP-142
```

Schlechte Beispiele sind „fix", „Änderungen" oder „asdf". Manche Teams nutzen eine Konvention wie **Conventional Commits** (Präfixe wie `feat:` oder `fix:`), wichtig ist vor allem, dass das Team einheitlich vorgeht (Sprache, Format).

Weitere Teamregeln: häufig und in kleinen Schritten committen, vor dem Push den aktuellen Stand des Hauptzweigs einholen, keine generierten Dateien, Zugangsdaten oder große Binärdateien einchecken (Ausschlüsse in der Datei `.gitignore` festhalten), niemals auf gemeinsame Zweige force-pushen und Releases mit Tags markieren. Für Versionsnummern nutzt man oft **Semantic Versioning** `MAJOR.MINOR.PATCH`: MAJOR steigt bei inkompatiblen Änderungen der Schnittstelle, MINOR bei neuen abwärtskompatiblen Funktionen, PATCH bei Fehlerbehebungen.

#### Q-9.3-13 · Git-Bereiche
**Anweisung:** Ordne die Situationen dem Bereich zu, in dem sich die Änderung gerade befindet.
- Datei bearbeitet und gespeichert, aber noch nicht vorgemerkt → Arbeitsverzeichnis
- Neue Datei, die Git noch nicht verfolgt, liegt im Projektordner → Arbeitsverzeichnis
- Die Änderung ist für den nächsten Commit vorgemerkt → Staging-Bereich (Index)
- Die Datei erscheint in git status unter „Zum Commit vorgemerkt" → Staging-Bereich (Index)
- Änderung ist committet, aber noch nicht hochgeladen → Lokales Repository
- Der Commit lässt sich offline mit git log ansehen → Lokales Repository
- Die Kolleginnen können den Commit erst jetzt abrufen → Remote-Repository
- Der Stand liegt auf dem Server und dient als gemeinsame Anlaufstelle → Remote-Repository
**Erklärung:** Der Weg einer Änderung führt vom Arbeitsverzeichnis über den Staging-Bereich (git add) ins lokale Repository (git commit) und von dort zum Remote (git push). Typische Verwechslung: „Gespeichert" heißt nur, dass die Datei im Arbeitsverzeichnis liegt — Git hat damit noch nichts festgehalten. Und ein Commit ist lokal gesichert, aber für das Team erst nach dem Push sichtbar.

#### Q-9.3-14 · Git-Bereiche
**Anweisung:** Ordne jeden Befehl dem Bereich zu, den er hauptsächlich verändert bzw. in dem sein Ergebnis landet.
- git add . (alle geänderten Dateien vormerken) → Staging-Bereich (Index)
- git restore --staged rechnung.py (Datei aus der Vormerkung nehmen) → Staging-Bereich (Index)
- git restore rechnung.py (Änderungen an der Datei verwerfen) → Arbeitsverzeichnis
- git commit -m "Rabatt ergänzt" (vorgemerkte Änderungen festhalten) → Lokales Repository
- git fetch origin (neue Commits holen, Dateien bleiben unverändert) → Lokales Repository
- git push origin main (lokale Commits übertragen) → Remote-Repository
- git push origin v1.2.0 (Tag zum Server übertragen) → Remote-Repository
**Erklärung:** add und restore --staged wirken auf den Index, restore auf die Dateien im Arbeitsverzeichnis, commit und fetch schreiben in das lokale Repository und push in das Remote. git pull kommt bewusst nicht vor: Es ist fetch plus merge und berührt deshalb mehrere Bereiche. Typische Verwechslung: fetch lädt zwar vom Remote, ändert aber nicht das Arbeitsverzeichnis.

#### Q-9.3-15 · Git-Bereiche
**Anweisung:** Ordne die Situationen dem Bereich zu, in dem sich die genannte Änderung bzw. der genannte Stand befindet.
- Nach git add wurde die Datei erneut geändert: Diese zweite Änderung steckt nur hier → Arbeitsverzeichnis
- Der Test läuft gegen die Dateien im Projektordner, auch mit uncommitteten Änderungen → Arbeitsverzeichnis
- Die vorgemerkte Fassung einer Datei, die beim nächsten Commit übernommen wird → Staging-Bereich (Index)
- Von einer Datei sollen mit git add -p nur zwei von fünf Änderungen in den Commit → Staging-Bereich (Index)
- Git meldet: Dein Zweig ist 2 Commits vor origin/main — diese 2 Commits liegen hier → Lokales Repository
- Ein halbfertiger Stand wird gesichert, ohne ihn anderen zu zeigen → Lokales Repository
- Drei neue Commits von Kolleg:innen, die noch nicht heruntergeladen wurden → Remote-Repository
- Der Merge-Request wird auf Basis dieser Fassung des Zweigs geprüft → Remote-Repository
**Erklärung:** Ein Merge-Request setzt voraus, dass der Zweig bereits auf dem Remote liegt; nur dort kann er geprüft werden. Wer nach git add noch weiterarbeitet, hat eine Fassung im Index und eine neuere im Arbeitsverzeichnis — der Commit enthält nur die vorgemerkte. Wichtig: „2 Commits vor origin/main" bezieht sich auf das lokale Repository, „3 Commits dahinter" auf Commits, die erst per fetch geholt werden müssen.

#### Q-9.3-16 · Git-Bereiche
**Anweisung:** Ordne die Aktionen dem Bereich zu, in dem die betroffene Änderung bzw. der betroffene Stand danach liegt.
- git reset --soft HEAD~1: Letzter Commit zurückgenommen, Änderungen bleiben vorgemerkt → Staging-Bereich (Index)
- Die Datei mit Konfliktmarkierungen wird im Editor bereinigt → Arbeitsverzeichnis
- git reset --mixed HEAD~1: Commit zurückgenommen, Änderungen nur noch in den Dateien → Arbeitsverzeichnis
- Die bereinigte Konfliktdatei wurde mit git add als gelöst markiert → Staging-Bereich (Index)
- git revert <hash>: Ein neuer Commit macht eine frühere Änderung rückgängig → Lokales Repository
- Der Tag v1.2.0 existiert, wurde aber noch nicht mit git push übertragen → Lokales Repository
- git push --force überschreibt die Historie, die Kolleg:innen bereits geholt haben → Remote-Repository
- Die CI-Pipeline startet automatisch, sobald hier ein neuer Commit eintrifft → Remote-Repository
**Erklärung:** reset --soft lässt die Änderungen im Staging-Bereich, reset --mixed (Standard) im Arbeitsverzeichnis, reset --hard würde sie verwerfen. git revert erzeugt einen neuen Commit im lokalen Repository und erhält die Historie. Tags liegen zunächst nur lokal und werden gesondert gepusht. Ein erzwungener Push überschreibt die gemeinsame Historie im Remote und ist deshalb auf geteilten Zweigen tabu. Typische Verwechslung: reset und revert — reset verschiebt den Zweigzeiger, revert fügt einen neuen Commit hinzu.
`schwierigkeit: schwer` · `bloom: analysieren`
