# Thema 4.3 — Systematische Fehlersuche und Automatisierung von Teilaufgaben

## Theorie

### Fehler gehören dazu — systematisch damit umgehen

Im Ausbildungsrahmenplan der FIAusbV ist für die fachrichtungsübergreifende Berufsbildposition „Entwickeln, Erstellen und Betreuen von IT-Lösungen" (§ 4 Abs. 2 Nr. 4) vorgesehen, Fehler systematisch zu erkennen, zu analysieren und zu beheben. Die Position „Programmieren von Softwarelösungen" (§ 4 Abs. 2 Nr. 10) nennt außerdem das Automatisieren von Teilaufgaben von IT-Systemen. Beides ist in allen vier Fachrichtungen gefragt: Ein Skript zur Client-Verwaltung bei der Brevanta IT-Systemhaus GmbH muss ebenso zuverlässig laufen wie die nächtliche Auswertung der Produktionsdaten eines Industriekunden oder die Verarbeitung von Sensorwerten in einer Smart Factory.

### Fehlerarten unterscheiden

- **Syntaxfehler:** Der Code verstößt gegen die Grammatik der Sprache. Compiler oder Interpreter melden ihn, bevor das Programm (oder die betroffene Stelle) läuft. Beispiel: Es fehlt ein Doppelpunkt.

```python
if temperatur > 8
    print("Alarm")
# SyntaxError: expected ':'
```

- **Laufzeitfehler:** Der Code ist syntaktisch korrekt, aber während der Ausführung tritt ein Problem auf, das zu einer Ausnahme (*Exception*) führt, z. B. Division durch null, Zugriff auf einen nicht vorhandenen Listenindex, eine nicht vorhandene Datei oder eine nicht umwandelbare Eingabe.

```python
werte = []
print(sum(werte) / len(werte))   # ZeroDivisionError: division by zero
int("abc")                       # ValueError
```

- **Logikfehler:** Das Programm läuft ohne Fehlermeldung, liefert aber ein falsches Ergebnis, weil die Idee oder die Bedingung falsch umgesetzt wurde. Das sind die tückischsten Fehler, weil niemand automatisch gewarnt wird.

```python
def ist_volljaehrig(alter):
    return alter > 18      # Logikfehler: 18-Jährige werden abgewiesen, richtig wäre >= 18

print(ist_volljaehrig(18)) # Ausgabe: False, obwohl True erwartet wird
```

Zusätzlich gibt es Fehler außerhalb des Codes: falsche oder unvollständige Anforderungen, fehlerhafte Eingabedaten, Konfigurations- oder Umgebungsprobleme (z. B. fehlende Berechtigung, falsche Version einer Bibliothek).

### Systematisch vorgehen

Wildes Probieren kostet Zeit und kann neue Fehler erzeugen. Ein bewährtes Vorgehen:

1. **Fehler reproduzieren:** Unter welchen Bedingungen tritt er auf? Mit welchen Eingabedaten? Ein Fehler, den man nicht auslösen kann, lässt sich kaum sicher beheben.
2. **Fehlermeldung lesen:** Fehlertyp, Meldung und die Stelle im Code (Zeilennummer) verstehen. Bei einem Python-Traceback steht die eigentliche Ausnahme in der letzten Zeile, darüber die Aufrufkette, die zum Fehler führte.
3. **Eingrenzen:** Ort und Ursache schrittweise einkreisen — z. B. Teile des Programms auskommentieren, Zwischenwerte ausgeben oder prüfen, ab welchem Punkt der Wert nicht mehr stimmt (Halbierungsprinzip: den Codeablauf in der Mitte prüfen und dann die fehlerhafte Hälfte weiter teilen).
4. **Hypothese bilden und prüfen:** Eine konkrete Vermutung aufstellen und gezielt testen, statt viele Änderungen gleichzeitig vorzunehmen.
5. **Beheben:** Die Ursache beseitigen, nicht nur das Symptom überdecken.
6. **Prüfen:** Mit dem ursprünglichen Fehlerfall und mit weiteren Testfällen kontrollieren, dass der Fehler weg ist und nichts anderes kaputtgegangen ist (Regressionstest).
7. **Dokumentieren:** Ursache, Lösung und gegebenenfalls einen neuen Testfall festhalten, damit der Fehler nicht wiederkehrt.

### Debugging und Logging

Ein **Debugger** ist ein Werkzeug der Entwicklungsumgebung, das ein Programm kontrolliert ausführt. Wichtige Funktionen:

- **Haltepunkt (Breakpoint):** Das Programm hält an einer markierten Zeile an.
- **Einzelschrittmodus:** Anweisung für Anweisung weitergehen (*Step over*: Funktionsaufruf als ein Schritt; *Step into*: in die Funktion hineinspringen).
- **Variablenüberwachung (Watch):** Aktuelle Werte von Variablen ansehen, ggf. beobachten, wann sie sich ändern.
- **Aufrufstapel (Call Stack):** Zeigt, über welche Funktionen die aktuelle Stelle erreicht wurde.

Wo ein Debugger nicht verfügbar ist — etwa bei einem Programm, das nachts auf einem Server läuft —, helfen **Logdateien**. Ein Programm schreibt dabei Ereignisse mit Zeitstempel und Schweregrad in eine Datei oder an einen zentralen Logdienst. Üblich sind die Stufen DEBUG (Detailinformationen für die Fehlersuche), INFO (normale Ereignisse), WARNING (ungewöhnlich, aber nicht kritisch), ERROR (eine Aktion ist fehlgeschlagen) und CRITICAL (schwerwiegender Fehler, Programm kaum noch funktionsfähig). Gegenüber einfachen `print`-Ausgaben lassen sich Logs filtern, dauerhaft speichern und nachträglich auswerten.

```python
import logging

logging.basicConfig(level=logging.INFO,
                    format="%(asctime)s %(levelname)s %(message)s")

def lese_messwert(text):
    try:
        wert = float(text)
    except ValueError:
        logging.error("Ungültiger Messwert: %r", text)
        return None
    logging.info("Messwert gelesen: %.1f", wert)
    return wert

lese_messwert("4.2")   # Log: ... INFO Messwert gelesen: 4.2
lese_messwert("abc")   # Log: ... ERROR Ungültiger Messwert: 'abc'
```

Der Block `try … except` ist die **Ausnahmebehandlung**: Tritt im `try`-Teil eine Ausnahme vom angegebenen Typ auf, wird der `except`-Teil ausgeführt, statt dass das Programm abstürzt. Wichtig ist, gezielt den erwarteten Fehlertyp abzufangen und den Fehler zu protokollieren, statt ihn stillschweigend zu ignorieren. In Logs gehören keine Passwörter, Zugangsdaten oder unnötigen personenbezogenen Daten.

### Testfälle als Absicherung

Zu jeder Funktion sollten einige Testfälle existieren: ein typischer Normalfall, Grenzwerte (z. B. genau 18 Jahre beim Alter) und Fehlerfälle (leere Liste, ungültige Eingabe). So werden Logikfehler wie `>` statt `>=` gefunden. Wer Fehler behebt, ergänzt einen Testfall, der den Fehler vorher aufgedeckt hätte.

### Teilaufgaben automatisieren

Automatisieren heißt, wiederkehrende, regelbasierte Aufgaben nicht mehr von Hand, sondern durch ein Skript oder Programm ausführen zu lassen. Typische Beispiele bei Brevanta: Konten für neue Mitarbeitende eines Kunden anlegen, Sicherungen erstellen, Logdateien archivieren, Messwerte jede Nacht aus Dateien einlesen und aufbereiten, Berichte per Zeitplan erzeugen. Vorteile: weniger Fehler durch Routinetätigkeit, Zeitersparnis, Reproduzierbarkeit, Dokumentation des Vorgehens im Skript selbst.

**Prinzip eines Skripts:** Eingaben bzw. Parameter einlesen, Aufgabe ausführen, Ergebnis prüfen, Ausgabe oder Log schreiben, definierten **Rückgabewert (Exit-Code)** liefern (üblich: 0 = Erfolg, ungleich 0 = Fehler), damit aufrufende Systeme den Erfolg auswerten können.

Skripte gibt es in verschiedenen Formen: **Batch-Dateien** (`.bat`) unter Windows für einfache Abläufe, **PowerShell** für Windows-Administration, **Shell-Skripte** (z. B. Bash) unter Linux/Unix sowie Skripte in allgemeinen Sprachen wie Python, die auf mehreren Plattformen laufen. Das Prinzip ist überall dasselbe: Befehle werden in einer Datei abgelegt und nacheinander ausgeführt, mit Variablen, Verzweigungen und Schleifen.

```bash
#!/bin/bash
# sichert ein Verzeichnis mit Datum im Dateinamen
quelle="/srv/daten"
ziel="/backup/daten_$(date +%Y-%m-%d).tar.gz"
tar -czf "$ziel" "$quelle" || { echo "Sicherung fehlgeschlagen" >&2; exit 1; }
echo "Sicherung erstellt: $ziel"
```

Das Skript erzeugt ein komprimiertes Archiv mit Tagesdatum im Namen; schlägt `tar` fehl, wird eine Meldung auf die Fehlerausgabe geschrieben und das Skript mit Exit-Code 1 beendet.

Ein Python-Beispiel, das Logdateien findet, die älter als 30 Tage sind (und sie zunächst nur auflistet, statt sie zu löschen):

```python
from datetime import datetime, timedelta
from pathlib import Path

grenze = datetime.now() - timedelta(days=30)
for datei in Path("/var/log/kundenportal").glob("*.log"):
    geaendert = datetime.fromtimestamp(datei.stat().st_mtime)
    if geaendert < grenze:
        print(f"Archivierungskandidat: {datei.name}")
```

### Zeitplanung und Betrieb automatisierter Aufgaben

Damit Skripte ohne manuellen Start laufen, setzt man einen **Zeitplaner** ein: unter Linux typischerweise `cron` (Konfiguration in einer Crontab), unter Windows die Aufgabenplanung (Task Scheduler). Eine Crontab-Zeile besteht aus fünf Zeitfeldern (Minute, Stunde, Tag des Monats, Monat, Wochentag) und dem Befehl:

```
30 2 * * 1-5 /opt/skripte/sicherung.sh
```

Diese Zeile startet das Skript montags bis freitags jeweils um 02:30 Uhr. Beim Betrieb automatisierter Skripte sollte man beachten:

- **Testen** in einer Testumgebung, bevor ein Skript produktiv und zeitgesteuert läuft; besonders vorsichtig bei löschenden Aktionen (zunächst nur auflisten).
- **Fehlerbehandlung und Logging**, damit ein nächtlicher Fehlschlag am nächsten Morgen nachvollziehbar ist; idealerweise eine Benachrichtigung bei Fehlern.
- **Wiederholbarkeit:** Ein Skript sollte bei erneutem Lauf keinen Schaden anrichten (kein doppeltes Anlegen, kein Überschreiben von Wichtigem).
- **Zugangsdaten** nicht im Klartext im Skript speichern, sondern über geschützte Konfiguration, Umgebungsvariablen oder einen Passwort-Tresor bereitstellen; Skripte laufen mit möglichst geringen Berechtigungen.
- **Dokumentation und Versionsverwaltung:** Zweck, Parameter, Zeitplan und Zuständigkeit festhalten.

- Zusammenspiel von Webanwendung und Datenbankschnittstelle prüfen → Integrationstest
- Das gesamte System gegen die Anforderungsspezifikation testen → Systemtest
- Der Kunde prüft in seiner Umgebung, ob die Lieferung den Vertrag erfüllt → Abnahmetest
- Abhängigkeiten werden durch Mocks oder Stubs ersetzt → Komponententest

#### Q-4.3-15 · Teststufen
**Anweisung:** Ordne die Testaktivitäten der passenden Teststufe zu.
- Entwickler:innen prüfen mit JUnit eine Rechenfunktion → Komponententest
- Test auf einer produktionsnahen Umgebung: Leistung, Last und Benutzbarkeit des Gesamtsystems → Systemtest
- Die Fachabteilung führt Anwendungsfälle mit realen Daten aus und gibt die Software frei → Abnahmetest

**Erklärung:** Im V-Modell korrespondiert der Abnahmetest mit der Anforderungsdefinition (Lastenheft) und der Systemtest mit dem Systementwurf (Pflichtenheft). Der Integrationstest prüft das Zusammenspiel, der Komponententest einzelne Bausteine.

#### Q-4.3-16 · Teststufen
**Anweisung:** Bei der Entwicklung einer Anwendung für einen Brevanta-Kunden fallen unterschiedliche Fehler auf. Ordne jeden Fall der Teststufe zu, in der er am ehesten entdeckt wird.
- Die Testsuite einer einzelnen Klasse läuft bei jedem Commit automatisch und meldet einen Rundungsfehler → Komponententest
- Beim Zusammenführen von Frontend und REST-API stimmen die Datumsformate nicht überein → Integrationstest
- Bei 500 gleichzeitigen Nutzern steigt die Antwortzeit über die im Pflichtenheft vereinbarten zwei Sekunden → Systemtest
- Der Kunde lehnt die Software ab, weil ein im Lastenheft geforderter Berichtstyp fehlt → Abnahmetest
- Nach einer Schemaänderung liefert die Datenbankschicht an die Geschäftslogik fehlerhafte Daten → Integrationstest
- Die Eingabevalidierung einer Funktion wird mit Grenzwerten geprüft und lässt einen ungültigen Wert zu → Komponententest
**Erklärung:** Fehler in einem einzelnen Baustein zeigt der Komponententest, Fehler an Schnittstellen der Integrationstest, Abweichungen vom Pflichtenheft im Gesamtsystem der Systemtest und Abweichungen vom Vertrag bzw. Lastenheft der Abnahmetest.
`schwierigkeit: schwer` · `bloom: analysieren`
