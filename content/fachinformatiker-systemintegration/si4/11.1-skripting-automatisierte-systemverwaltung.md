# Thema 11.1 — Skripte zur automatisierten Systemverwaltung

## Theorie

### Einordnung

Im Prüfungsbereich „Konzeption und Administration von IT-Systemen" soll nachgewiesen werden, dass Programme zur automatisierten Systemverwaltung erstellt werden können (§ 21 Absatz 1 Nummer 4 FIAusbV); die Aufgaben sind schriftlich zu bearbeiten, die Prüfungszeit beträgt 90 Minuten. Der Ausbildungsrahmenplan nennt dazu das Automatisieren von Teilaufgaben von IT-Systemen (Anlage Abschnitt A lfd. Nr. 10 c). In der Fachrichtung Systemintegration gehört außerdem das Administrieren von IT-Systemen zu den berufsprofilgebenden Inhalten (Abschnitt C lfd. Nr. 3), etwa das Überwachen von Systemauslastung und Systemverhalten.

Das Thema 4.3 des fachrichtungsübergreifenden Teils hat bereits Grundlagen vermittelt: Fehlerarten, Debugging und das Prinzip „Skript = gespeicherte Befehlsfolge". Hier geht es um den **administrationsnahen Betrieb**: Wie sieht ein Skript aus, das nachts unbeaufsichtigt auf Kundenservern läuft, und worauf muss man achten, damit es keinen Schaden anrichtet?

### Typische Aufgaben in der Systemverwaltung

Im Managed-Services-Betrieb der **Brevanta IT-Systemhaus GmbH** betreut ein kleines Team mehrere hundert Server und Arbeitsplätze von Kunden. Wiederkehrende, klar beschreibbare Aufgaben werden deshalb automatisiert:

- **Benutzerverwaltung:** Konten aus einer Liste (z. B. CSV-Datei der Personalabteilung des Kunden) anlegen, Gruppen zuweisen, Konten ausgeschiedener Mitarbeitender sperren.
- **Logrotation und Aufräumen:** Logdateien komprimieren, nach einer Aufbewahrungsfrist löschen, temporäre Dateien entfernen, damit Datenträger nicht volllaufen.
- **Datensicherung:** Verzeichnisse oder Datenbanken sichern, Sicherungen auf Vollständigkeit prüfen, alte Sicherungen entfernen.
- **Berichte und Überwachung:** Plattenfüllstand, Dienststatus oder Updatestand einsammeln und als Bericht oder Warnmeldung versenden.
- **Wartung:** Dienste in definierter Reihenfolge neu starten, Zertifikatsablauf prüfen, Inventardaten abfragen.

Vorteile sind weniger Routinefehler, reproduzierbare Abläufe, Zeitersparnis und ein selbstdokumentierendes Vorgehen. Nicht jede Aufgabe lohnt sich: Einmalige, selten wiederkehrende oder schlecht beschreibbare Tätigkeiten (viele Ausnahmen, Entscheidungen nach Gefühl) werden besser manuell erledigt, solange der Aufwand für Erstellung, Test und Pflege höher wäre als der Nutzen.

### Skriptsprachen im Überblick

Das Prinzip ist in allen Sprachen gleich: Befehle werden in einer Datei abgelegt und mit Variablen, Verzweigungen und Schleifen verknüpft. Unterschiede liegen im Einsatzgebiet:

| Sprache | typisches Einsatzgebiet | Besonderheit |
|---|---|---|
| Bash (Shell) | Linux/Unix-Server | Verkettet vorhandene Programme; Pipes übergeben **Text** |
| PowerShell | Windows-Administration (auch plattformübergreifend verfügbar) | Pipelines übergeben **Objekte** mit Eigenschaften |
| Python | plattformübergreifend, komplexere Logik | Umfangreiche Standardbibliothek, gut lesbar, gut testbar |
| Batch (.bat) | einfache Windows-Abläufe | begrenzter Funktionsumfang, heute meist durch PowerShell ersetzt |

Die Wahl richtet sich nach Zielsystem, vorhandenen Kenntnissen im Team, Komplexität und Wartbarkeit. Für „drei Befehle hintereinander" genügt ein Shell-Skript, für Auswertungen mit Datenstrukturen und Fehlerbehandlung ist Python meist besser lesbar.

Ein PowerShell-Beispiel für den Testlauf-Gedanken: Der Schalter `-WhatIf` zeigt nur an, was geschehen würde, ohne zu löschen.

```powershell
Get-ChildItem -Path "D:\Logs" -Filter *.log |
    Where-Object { $_.LastWriteTime -lt (Get-Date).AddDays(-30) } |
    Remove-Item -WhatIf
```

Erst wenn die Ausgabe der Erwartung entspricht, wird `-WhatIf` entfernt.

### Aufbau eines Betriebsskripts

Ein robustes Betriebsskript folgt einem festen Schema: Parameter einlesen, Eingaben und Voraussetzungen prüfen, Aufgabe ausführen, Ergebnis prüfen, Protokoll schreiben, definierten Exit-Code zurückgeben. Das folgende Bash-Skript sichert ein Verzeichnis und entfernt alte Sicherungen:

```bash
#!/bin/bash
# sicherung.sh - sichert ein Verzeichnis und entfernt alte Sicherungen
# Aufruf:  sicherung.sh QUELLE ZIELVERZEICHNIS [AUFBEWAHRUNG_TAGE]
# Exit-Codes: 0 = Erfolg, 2 = falscher Aufruf, 3 = Quelle fehlt, 4 = Sicherung fehlgeschlagen
set -u

QUELLE="${1:-}"
ZIEL="${2:-}"
TAGE="${3:-14}"
LOG="/var/log/brevanta/sicherung.log"

log() { echo "$(date '+%Y-%m-%d %H:%M:%S') $*" >> "$LOG"; }

if [ -z "$QUELLE" ] || [ -z "$ZIEL" ]; then
    echo "Aufruf: $0 QUELLE ZIELVERZEICHNIS [TAGE]" >&2
    exit 2
fi
if [ ! -d "$QUELLE" ] || [ ! -d "$ZIEL" ]; then
    log "FEHLER: Quelle oder Ziel nicht vorhanden ($QUELLE, $ZIEL)"
    exit 3
fi

archiv="$ZIEL/daten_$(date +%Y-%m-%d).tar.gz"
if tar -czf "$archiv" -C "$QUELLE" . ; then
    log "INFO: Sicherung erstellt: $archiv"
else
    log "FEHLER: tar fehlgeschlagen fuer $QUELLE"
    rm -f "$archiv"
    exit 4
fi

find "$ZIEL" -name 'daten_*.tar.gz' -mtime +"$TAGE" -delete
log "INFO: Alte Sicherungen entfernt (Aufbewahrung: $TAGE Tage)"
exit 0
```

Was das Skript zeigt: Die Parameter werden mit Standardwert gelesen (`${3:-14}` setzt 14, wenn kein dritter Parameter übergeben wurde). `set -u` bricht ab, wenn eine nicht gesetzte Variable verwendet wird — das schützt vor Tippfehlern in Variablennamen. Variablen stehen in Anführungszeichen, damit Pfade mit Leerzeichen funktionieren. Fehlermeldungen zur Bedienung gehen auf die **Fehlerausgabe** (`>&2`), Betriebsereignisse in die Logdatei. Das Log-Verzeichnis ist vorab angelegt und für das Dienstkonto beschreibbar. Die Alte-Dateien-Bereinigung läuft erst nach einer erfolgreichen Sicherung — sonst würde ein Fehlerfall die letzten guten Sicherungen auch noch löschen.

### Python-Beispiel: Benutzer aus einer Liste anlegen

Dieses Python-Skript liest eine CSV-Datei (Spalten `name;gruppe`) und legt fehlende Linux-Konten an. Es kann mit `--testlauf` aufgerufen werden und ändert dann nichts:

```python
import csv
import subprocess
import sys

def benutzer_existiert(name):
    return subprocess.run(["id", name], capture_output=True).returncode == 0

def anlegen(name, gruppe, testlauf):
    if benutzer_existiert(name):
        print(f"UEBERSPRUNGEN {name}: existiert bereits")
        return True
    befehl = ["useradd", "-m", "-G", gruppe, name]
    if testlauf:
        print("TESTLAUF:", " ".join(befehl))
        return True
    ergebnis = subprocess.run(befehl, capture_output=True, text=True)
    if ergebnis.returncode != 0:
        print(f"FEHLER {name}: {ergebnis.stderr.strip()}", file=sys.stderr)
        return False
    print(f"OK {name} angelegt")
    return True

def main():
    if len(sys.argv) < 2:
        print("Aufruf: neue_benutzer.py DATEI.csv [--testlauf]", file=sys.stderr)
        return 2
    testlauf = "--testlauf" in sys.argv
    fehler = 0
    with open(sys.argv[1], newline="", encoding="utf-8") as f:
        for zeile in csv.DictReader(f, delimiter=";"):
            if not anlegen(zeile["name"], zeile["gruppe"], testlauf):
                fehler += 1
    return 1 if fehler else 0

if __name__ == "__main__":
    sys.exit(main())
```

Wichtige Punkte: Das Skript prüft vor dem Anlegen, ob das Konto schon existiert (Idempotenz, siehe unten). Der Befehl wird als Liste übergeben, nicht als zusammengesetzter Text; so kann ein Name mit Sonderzeichen keine zusätzlichen Befehle einschleusen. Ein Fehler bei einem Konto bricht die Verarbeitung der übrigen nicht ab, wird aber gezählt und im Exit-Code (1) gemeldet. **Es steht kein Kennwort im Skript:** Die Erstanmeldung wird über ein geeignetes Verfahren geregelt (z. B. Zwangswechsel beim ersten Login oder zentrales Konto-Management), nicht über eine Klartextspalte in der CSV-Datei.

### Fehlerbehandlung, Exit-Codes und Logging

- **Exit-Code (Rückgabewert):** Jedes Programm liefert beim Ende eine Zahl. Konvention: **0 = Erfolg**, jeder andere Wert = Fehler; die Bedeutung der Werte legt man im Skriptkopf fest (wie oben 2, 3, 4). In Bash steht der Wert des letzten Befehls in `$?`. Zeitplaner, Überwachungssysteme und aufrufende Skripte werten ihn aus. Ein Skript, das am Ende immer `exit 0` meldet, obwohl Schritte fehlgeschlagen sind, täuscht die Überwachung.
- **Befehle prüfen:** Der Erfolg kritischer Schritte wird direkt geprüft (`if tar ...; then`, `befehl || exit 1`). In Bash hilft `set -u` gegen nicht gesetzte Variablen; `set -o pipefail` sorgt dafür, dass eine Pipeline als fehlgeschlagen gilt, wenn irgendein Teil fehlschlägt, nicht nur der letzte.
- **Ausgabekanäle:** Normale Ausgabe geht an die Standardausgabe (stdout), Fehlermeldungen an die Fehlerausgabe (stderr). So lassen sich beide getrennt umleiten und auswerten.
- **Logging:** Jeder Lauf schreibt nachvollziehbare Einträge mit **Zeitstempel**, **Schweregrad** (INFO, WARNUNG, FEHLER), **Meldung** und genügend Kontext (welche Datei, welcher Server). Passwörter und andere Geheimnisse gehören nie ins Log. Logs werden selbst rotiert, damit sie nicht den Datenträger füllen.
- **Benachrichtigung:** Ein Fehler, den niemand bemerkt, ist kein behandelter Fehler. Bei kritischen Aufgaben löst ein Exit-Code ungleich 0 eine Meldung an das Monitoring oder eine E-Mail an das zuständige Team aus.

### Zeitplanung mit Cron und Aufgabenplanung

Unter Linux startet **cron** Aufgaben zeitgesteuert, unter Windows übernimmt das die **Aufgabenplanung** (Task Scheduler). Eine Crontab-Zeile hat fünf Zeitfelder und den Befehl: Minute, Stunde, Tag des Monats, Monat, Wochentag.

```
15 1 * * * /opt/brevanta/sicherung.sh /srv/daten /backup >> /var/log/brevanta/cron.log 2>&1
*/15 * * * * /opt/brevanta/pruefe_dienste.sh
0 3 * * 0 /opt/brevanta/bericht_wochenstart.sh
```

Die erste Zeile startet die Sicherung täglich um 01:15 Uhr und leitet Standard- und Fehlerausgabe in eine Datei um. Die zweite läuft alle 15 Minuten. Die dritte läuft sonntags um 03:00 Uhr (Wochentag 0 steht für Sonntag). Ein Stern bedeutet „jeder Wert", `1-5` ein Bereich, `*/15` ein Intervall.

Praxisregeln: Cron startet Skripte in einer **minimalen Umgebung** (kaum Umgebungsvariablen, eingeschränkter Suchpfad). Deshalb werden in Zeitplänen und Skripten **absolute Pfade** verwendet; ein Skript, das interaktiv funktioniert, aber im Zeitplan scheitert, hat meist hier seine Ursache. Läuft ein Lauf länger als das Intervall, können sich Instanzen überlappen; eine **Sperrdatei** (z. B. mit dem Hilfsprogramm `flock`) verhindert, dass zwei Läufe gleichzeitig dieselben Daten bearbeiten. Zeitpläne werden dokumentiert (Zweck, Zuständigkeit, Wartungsfenster), und das ausführende Konto bekommt nur die nötigen Rechte.

### Idempotenz und Testlauf

Ein Skript ist **idempotent**, wenn mehrfaches Ausführen dasselbe Ergebnis hat wie einmaliges: Das Anlegen eines bereits vorhandenen Kontos wird übersprungen statt Fehler oder Doppelanlage zu erzeugen, ein vorhandenes Verzeichnis wird nicht erneut angelegt, eine Zeile wird nur dann in eine Konfigurationsdatei eingetragen, wenn sie dort noch nicht steht. Das macht Wiederholung nach einem Abbruch ungefährlich und ist die Grundlage der deklarativen Konfigurationsverwaltung (Thema 11.3).

Zum sicheren Entwickeln gehört ein **Testlauf (Dry-Run)**: Das Skript gibt aus, was es tun würde, ohne es zu tun (im Beispiel `--testlauf`, in PowerShell `-WhatIf`). Zusätzlich wird zuerst in einer Testumgebung mit Testdaten geprüft; löschende Aktionen listen anfangs nur auf.

Ein klassischer Fehler zeigt, warum Prüfungen nötig sind: Der Befehl `rm -rf "$ZIEL"/*` löscht bei einer leeren oder nie gesetzten Variable `ZIEL` alles unterhalb der Wurzel des Dateisystems. Schutz: Variablen auf Inhalt prüfen (`set -u` fängt nur ungesetzte Variablen ab; gegen leere hilft `${ZIEL:?}` oder eine Prüfung mit `[ -n "$ZIEL" ]`), vor dem Löschen kontrollieren, dass das Verzeichnis existiert und der erwartete Pfad ist.

### Sicherheit von Skripten

- **Keine Klartext-Passwörter** im Skript, in der Crontab, in Kommentaren oder im Versionsverwaltungs-Repository. Zugangsdaten kommen aus geschützten Quellen: eine nur vom Dienstkonto lesbare Konfigurationsdatei, Umgebungsvariablen aus einem Geheimnis-Verwaltungssystem, Schlüsselpaare (z. B. SSH-Schlüssel mit eingeschränkter Berechtigung) oder das Berechtigungsmodell des Betriebssystems selbst. Kennwörter stehen auch nicht in Befehlszeilenparametern, weil diese in Prozesslisten sichtbar sein können.
- **Minimale Rechte:** Jedes Skript läuft unter einem eigenen Dienstkonto mit genau den nötigen Berechtigungen, nicht pauschal als Administrator oder `root`.
- **Schutz der Skriptdatei:** Schreibrechte nur für Berechtigte; wer die Datei ändern kann, kann in deren Namen beliebigen Code ausführen lassen.
- **Eingaben validieren:** Parameter, Dateinamen und CSV-Inhalte sind nie vertrauenswürdig. Befehle werden nicht aus ungeprüften Texten zusammengebaut.
- **Nachvollziehbarkeit:** Skripte liegen in der Versionsverwaltung, haben einen Kopfkommentar (Zweck, Parameter, Exit-Codes, Zuständigkeit) und werden geprüft, bevor sie produktiv laufen.

## Quiz

#### Q-11.1-01 · Multiple Choice
**Frage:** Ein Skript beendet sich mit dem Exit-Code 0. Was bedeutet das nach üblicher Konvention?
- [x] Das Skript meldet, dass es erfolgreich beendet wurde

- [ ] Das Skript hat einen schweren Fehler gemeldet
- [ ] Das Skript wartet auf eine Eingabe
**Erklärung:** 0 steht für Erfolg, alle anderen Werte für Fehler; der Wert sagt aber nur, was das Skript meldet, nicht, ob es alles richtig gemacht hat.

#### Q-11.1-02 · Zuordnung

- stderr ↔ Ausgabekanal für Fehlermeldungen
**Erklärung:** Zeitplaner starten Skripte ohne manuellen Eingriff; Exit-Code und Fehlerausgabe machen Fehler für Aufrufer und Überwachung auswertbar.

#### Q-11.1-04 · Lückentext (Wortauswahl)

#### Q-11.1-11 · Multiple Choice

- [ ] Den Befehl ohne Anführungszeichen schreiben

#### Q-11.1-12 · Multiple Choice
**Frage:** Ein Skript funktioniert bei manuellem Start, schlägt aber im Cron-Lauf fehl, weil Programme nicht gefunden werden. Was ist die wahrscheinlichste Ursache?
