# @edukedo/web

React + TypeScript + Vite Frontend (siehe Architekturplanung Abschnitt 2, 3, 5).

## Stand

- **Minimales Grundgerüst:** Vite + React + TypeScript, tRPC-Client (`@trpc/react-query` + TanStack Query v4) typsicher gegen `@edukedo/api` verdrahtet (`src/trpc.ts`).
- **PWA-Grundgerüst (F-40/F-41):** `vite-plugin-pwa` (`vite.config.ts`) — Web-App-Manifest + App-Shell-Precaching, installierbar. Platzhalter-Icons unter `public/icons/`. Volle Offline-Synchronisierung (F-42) ist bewusst nicht Teil davon, siehe Architekturplanung Abschnitt 13.
- **Offline-Modus (F-42), vollständig umgesetzt (alle sechs Bausteine):** `src/offlineDb.ts` legt das lokale IndexedDB-Schema über Dexie.js an (`content`: offline verfügbare Karteikarten/Quiz-Items inkl. Lösung; `queue`: noch nicht synchronisierte Lern-Ereignisse mit Zeitstempel + Client-UUID). Der FSRS-Scheduler und die Quiz-Prüflogik liegen dafür jetzt in `@edukedo/shared` (`fsrs/scheduler.ts`, `quiz-logic.ts`), damit Client und Server denselben Code nutzen. `src/OfflineDownload.tsx` (im "Fortschritt"-Tab) lädt per Klick über `offline.downloadKurs` den vollständigen Karteikarten-/Quiz-Bestand des aktiven Kurses in `offlineDb.content` — ein erneuter Download aktualisiert bestehende Einträge statt sie zu duplizieren. `src/useOnlineStatus.ts` erkennt einen Verbindungswechsel; `Flashcards.tsx`/`Quiz.tsx` lesen dann aus `offlineDb.content` statt vom Server und werten Antworten lokal aus (`src/offlineFlashcards.ts`/`src/offlineQuiz.ts`), inkl. Eintrag in die Sync-Warteschlange. `src/offlineSync.ts` überträgt diese Warteschlange über `offline.syncQueue`, sobald `src/useOfflineSync.ts` einen Wechsel zu `online` erkennt (automatisch, ohne eigene Nutzer-Interaktion) — nur die vom Server bestätigten Einträge werden danach lokal gelöscht, alles andere bleibt für einen späteren Versuch stehen. `src/OfflineStatus.tsx` (im Header, siehe `App.tsx`) macht das sichtbar: "Offline"-Hinweis inkl. Live-Zähler ausstehender Ereignisse (`src/useOfflineQueueCount.ts`, reaktiv über Dexie-Table-Hooks statt Polling), "Wird synchronisiert…", eine kurz sichtbare "✓ Synchronisiert"-Bestätigung sowie ein bleibender Fehlerhinweis bei nicht übernommenen Ereignissen. Siehe Architekturplanung Abschnitt 13 für den vollständigen Architekturansatz.
- **Auth-Seite:** Register-/Login-Formular gegen die bestehenden `auth.register`/`auth.login`/`auth.logout`/`auth.me`-Endpunkte (`src/App.tsx`).
- **Design-System (`src/styles.css`):** Design-Tokens (Farben inkl. Dark-Mode-Varianten, Schriften Fredoka/Manrope/JetBrains Mono) aus dem Entwurf `design/01-landing-und-app-vorschau.html` übernommen (siehe `design/README.md` und Architekturplanung Abschnitt 13) — kein Tailwind/shadcn, reines CSS mit Custom Properties.
- **Öffentliche Landing Page:** `src/LandingPage.tsx` — Marketing-Startseite (Hero, Mission, Kursvorstellung, Methode) für nicht eingeloggte Besucher:innen, als lokaler Anzeigezustand in `App.tsx` verdrahtet (`showAuth`), nicht als eigene Route. CTAs wechseln auf das bestehende Login-/Registrierungsformular. Siehe Architekturplanung Abschnitt 13.
- **Globaler Header (Layout-Vereinheitlichung, siehe Architekturplanung Abschnitt 13):** `src/Header.tsx` — dieselbe Kopfzeile (Logo + rechte Aktionen) auf wirklich allen Seiten, nicht nur der Landing Page: eingeloggte App, Login/Registrierung, Eltern-Dashboard, Vorschau, Rechtsseiten. `src/GuestHeaderActions.tsx` liefert die rechten Aktionen (Anmelden/Kostenlos starten) für alle nicht eingeloggten Zustände. Löst den zuvor nur teilweise behobenen Bruch zwischen der offenen Landing-Page-Kopfzeile und der in eine einzelne `.shell > .card` gepressten restlichen App ab.
- **Flip-Card (`src/FlipCard.tsx`):** Wiederverwendbare 3D-Flip-Interaktion (Frage-/Antwortseite), genutzt von `Flashcards.tsx` (ersetzt den früheren "Antwort zeigen"-Button) und von der Landing Page (Beispiel-Karteikarte im Hero).
- **Konto-Selbstlöschung (F-06):** `src/DeleteAccount.tsx` — Bestätigungsdialog mit Passworteingabe, ruft `auth.deleteAccount`.
- **Mehrfach-Kursbelegung aktiv genutzt (F-09):** `src/CourseSwitcher.tsx` — jetzt ein Dropdown im globalen Header (`.header-menu`, siehe Layout-Vereinheitlichung) statt großer Kacheln im Hauptbereich; eingeschriebene Kurse zur Auswahl, weitere veröffentlichte Kurse zum Beitreten. Der aktive Kurs (`App.tsx`, `selectedKursId`, fällt automatisch auf den ersten eingeschriebenen Kurs zurück) wird als `kursId`-Prop an Theorie/Karteikarten/Quiz/Fortschritt durchgereicht — alle vier zeigen jetzt nur noch Inhalte/Fortschritt des ausgewählten Kurses statt über alle eingeschriebenen Kurse hinweg zu aggregieren. Siehe Architekturplanung Abschnitt 13.
- **Nutzer-Menü im Header:** `src/UserMenu.tsx` — bündelt Rolle/Logout/Konto-löschen (löst die bisherige, mitten im Lernbereich stehende "Eingeloggt als ..."-Zeile ab) sowie, nur für `role === "admin"`, den Umschalter in den separaten Admin-Bereich. `src/useClickOutside.ts` schließt Header-Dropdowns (Kurs-/Nutzer-Menü) bei Klick außerhalb.
- **Karteikarten-Modus (F-20):** `src/Flashcards.tsx` — fällige Karten anzeigen, per Flip-Card (`src/FlipCard.tsx`) umdrehen, Selbsteinschätzung (nicht gewusst/unsicher/gewusst) an `progress.submitReview` melden.
- **Theorie-Ansicht:** `src/Theorie.tsx`, neuer Tab — Themen-Auswahl (TOC) plus Fließtext-Anzeige (`content.theorySections`); einfacher, selbst geschriebener Markdown-zu-JSX-Renderer für `###`-Zwischenüberschriften und `**fett**` statt einer zusätzlichen Bibliothek, da der Theorie-Content nur diese zwei Konstrukte nutzt.
- **Quiz-Modus (F-21, alle vier Formate):** `src/Quiz.tsx` — Multiple Choice (Option wählen), Zuordnung (Paare per Klick bilden), Lückentext (Inline-Eingabefelder), Kurzantwort (freies Textfeld); Server prüft und liefert Feedback, Abschluss-Score über alle Formate hinweg. Die vier Schritt-Komponenten liegen in `src/QuizSteps.tsx` und werden auch von `Vorschau.tsx` wiederverwendet (siehe unten).
- **Fortschrittsanzeige (F-30), inkl. Quiz-Ergebnissen (F-26):** `src/Progress.tsx` — Fortschrittsbalken je Fachgebiet und (eingerückt) je Thema, mit Prozent "beherrscht" und Bruchzahl; zählt jetzt Karteikarten und alle vier Quiz-Formate zusammen. `src/Quiz.tsx` invalidiert `progress.overview` nach jeder Antwort, damit der Fortschritt-Tab nicht auf einem veralteten Stand hängen bleibt.
- **Restzeit-/Lernpensum-Anzeige (F-35):** `src/Zielplanung.tsx`, oben im "Fortschritt"-Tab — zeigt je nach Kurs-Zielmodus (`kurs.targetMode`) entweder einen Zieltermin-Countdown ("einzeltermin": verbleibende Themen ÷ verbleibende Wochen, Rückstands-Warnung, Formular für Zieltermin/Plan-Start) oder ein wiederkehrendes Wochenziel ("wochenziel": Formular für ein Lerneinheiten-Pensum pro Woche, Fortschrittsbalken gegen die letzten rollierenden 7 Tage). Beide Modi laufen über `progress.pacing`, das Setzen der Zielwerte über `courses.setTarget`. Siehe Architekturplanung Abschnitt 13.
- **Barrierefreiheit (F-44), punktueller Durchgang über wiederverwendete Bausteine:** Sprungmarke zum Hauptinhalt (`.skip-link` in `Header.tsx`, zielt auf `id="main-content"` auf jedem `<main>`). Die drei Tab-/Segmented-Leisten (Lernmodus in `App.tsx`, Login/Registrieren ebenda, Prüfungsvorbereitung in `Pruefungsvorbereitung.tsx`) nutzen jetzt das volle ARIA-Tablist-Muster mit roving Tabindex und Pfeiltasten-Navigation (`src/tabListKeyboardNav.ts`, gemeinsam genutzt). Header-Dropdowns (Kurs-/Nutzer-Menü) schließen jetzt auch per Escape, mit Fokus-Rückgabe an den Auslöser (`src/useDismissableMenu.ts`, vormals `useClickOutside.ts`). `FlipCard.tsx` blendet die jeweils unsichtbare Kartenseite per `aria-hidden` auch für Screenreader aus (vorher lagen Frage und Antwort unabhängig vom Umdreh-Zustand gleichzeitig im Accessibility-Tree) und trägt `aria-pressed`. Elf verstreute Fehlertexte zu `src/ErrorMessage.tsx` (`role="alert"`) zusammengeführt. Neue, dediziert für weißen Text auf Flächen kalibrierte Farbtokens (`--coral-fill`/`--sprout-fill`/`--danger-fill`) lösen einen WCAG-AA-Kontrastverstoß bei Haupt-CTA-Button/aktiven Tabs/Karteikarten-Rückseite, ohne die vielfach wiederverwendeten Basisfarben selbst zu ändern. Siehe Architekturplanung Abschnitt 13.
- **Eltern-Consent-Flow (F-08, Kernmechanismus):** Registrierungsformular fragt bei unter 16-Jährigen zusätzlich die E-Mail eines Elternteils ab (`src/App.tsx`, `needsParentEmail`) und zeigt nach dem Absenden einen Sperrhinweis inkl. Dev-Bestätigungslink (`devConfirmUrl`, solange kein echter E-Mail-Versand angebunden ist). `src/ConsentConfirm.tsx` ist die öffentliche, loginlose Zielseite `/consent/confirm?token=...` des Bestätigungslinks (bestätigt, loggt den Elternteil automatisch ein und verlinkt weiter zum Eltern-Dashboard), direkt per `window.location.pathname`-Weiche in `src/main.tsx` gerendert (kein eigener Router im Projekt).
- **Eltern-Dashboard-Grundgerüst (F-90):** `src/ParentDashboard.tsx`, Route `/parent` — Login-Formular (falls noch keine Parent-Session), einmaliges Setzen eines eigenen Passworts (falls `passwordSet === false`), danach Liste verknüpfter Kinder mit Einwilligungsstatus und Widerruf-Button (mit Bestätigungsschritt, analog zu `DeleteAccount.tsx`).
- **Kindgerechte Datenschutz-Kurzfassung (F-53):** `src/DatenschutzKinder.tsx`, statische Seite unter `/datenschutz-kinder`, verlinkt aus Registrierungsformular, Sperrhinweis und Eltern-Dashboard. Bewusst als ungeprüfter Entwurf gekennzeichnet, da die vollständige juristische Fassung (F-51) im Projekt noch nicht existiert, siehe Architekturplanung Abschnitt 13.
- **Kontoloser Vorschau-Modus (F-08):** `src/Vorschau.tsx`, Route `/vorschau` (kein Login) — 5 zufällige Demo-Fragen aus allen veröffentlichten Kursen, verlinkt vom Sperrhinweis nach Registrierung einer/eines Minderjährigen. Nutzt dieselben Schritt-Komponenten wie `Quiz.tsx` (`src/QuizSteps.tsx`), nur gegen die öffentlichen `preview.*`-Endpunkte statt `quiz.*`.
- **Admin-/Redaktionsbereich, erste Version (F-11):** `src/AdminPanel.tsx` — Kursliste mit Veröffentlichen/Zurückziehen-Button je Kurs, plus ein "Content neu importieren"-Button (F-17, ruft `admin.triggerImport`), nur sichtbar für `role === "admin"` (`App.tsx`, kein eigener Account-Typ, keine eigene Route). Löst den bisherigen Weg ab, `kurs.is_published` und den Content-Import ausschließlich per SQL/CLI zu setzen bzw. auszulösen. Seit der Layout-Vereinheitlichung (siehe Architekturplanung Abschnitt 13) eine eigene Ansicht (`App.tsx`-`view`-Zustand, umgeschaltet über `UserMenu`) statt eines Inline-Anhängsels über der Kursliste.
- **Dev-Proxy:** `vite.config.ts` leitet `/api` an `http://localhost:3001` (apps/api) weiter, damit Session-Cookies im Dev-Modus ohne CORS-Klimmzüge funktionieren.
- **Business-Lizenzen, Auth-Grundgerüst (F-91, Baustein 1 von 6, Iteration 6):** `src/CompanyDashboard.tsx`, Route `/company` (analog zu `ParentDashboard.tsx`) — Login-Formular (falls noch keine Company-Session), einmaliges Setzen eines eigenen Passworts (falls `passwordSet === false`), danach Kontodaten (Name, Sitzplatz-Kontingent, Abrechnungsstatus). `src/CompanySetup.tsx`, Route `/company/setup?token=...` (analog zu `ConsentConfirm.tsx`) ist die öffentliche, loginlose Zielseite des vom Admin ausgelösten Setup-Links. `AdminPanel.tsx` bekam einen neuen Bereich zum Anlegen von Unternehmens-Konten (inkl. Anzeige des Setup-Links, solange kein echter E-Mail-Versand angebunden ist). Branding (F-92) und aggregierte Statistik (F-93) sind eigene, spätere Bausteine.
- **Business-Lizenzen, Einladungscodes + Mitgliedschaft (F-91, Baustein 2 von 6):** `CompanyDashboard.tsx` bekam zwei neue Bereiche — Einladungscodes erstellen/widerrufen und Teilnehmende-Liste (E-Mail/Beitrittsdatum) mit Lizenzentzug, dazu ein "X von Y belegt"-Sitzplatz-Zähler in `company.me`. Neue `src/RedeemCompanyCode.tsx`, im "Fortschritt"-Tab (`Progress.tsx`) neben Zielplanung/Offline-Download platziert, da es sich um eine kontobezogene, nicht lernmodus-spezifische Einstellung handelt — löst `company.redeemInviteCode` aus.
- **Business-Lizenzen, Branding (F-91/F-92, Baustein 3 von 6):** `CompanyDashboard.tsx` bekam eine neue `BrandingSection` (Logo-URL/Farbe/Begrüßungstext, mit Live-Vorschau) zum Pflegen von `company.updateBranding`. Neue `src/CompanyBranding.tsx` zeigt das Branding des zugeordneten Unternehmens (`company.myBranding`) als Banner oberhalb der Lernmodus-Tabs in `App.tsx` — bewusst ohne Interaktivität/Tracking, reiner Reputationswert. `RedeemCompanyCode.tsx` invalidiert `company.myBranding` nach erfolgreichem Einlösen, damit das Banner sofort erscheint, ohne dass die Seite neu geladen werden muss.
- **Business-Lizenzen, aggregierte Statistik (F-91/F-93, Baustein 4 von 6):** `CompanyDashboard.tsx` bekam eine neue `StatsSection` (Anteil aktiver Lizenzen, Ø Trefferquote, Ø Fortschritt aus `company.stats`) im selben `stat-section`/`stat-tile`-Vokabular wie "Deine Lernstatistik" in `Progress.tsx`. Unterhalb der serverseitigen Mindestgröße zeigt sie einen erklärenden Hinweistext statt Kennzahlen.
- **Noch offen:** granulare Kind-Berechtigungen im Eltern-Dashboard (F-90, setzt Gamification F-66 voraus), vollständige juristische Datenschutzerklärung/Impressum/AGB (F-51).
